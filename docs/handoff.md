# 交接系统

交接文档是给下一个会话的合同，不是聊天总结。只写它需要知道、否则会做错或重做的事。

## 什么时候交接

- 一个阶段做完，并且验证过了。
- 同一个问题连续卡住两次。
- 上下文明显变满（TUI 侧栏接近上限）。
- 用户要换一个不相关的任务。
- 用户明确说「交接」。

同一任务里的小修小补不要交接。

## 写到哪里

- 项目内：`.opencode/handoff/<YYYY-MM-DD>-<slug>.md`
- 没有项目目录：`~/.config/opencode/handoff/<YYYY-MM-DD>-<slug>.md`
- 记得把 `.opencode/handoff/` 加进 `.gitignore`

## 模板

```md
---
date: YYYY-MM-DD
source_session: sess_xxx
task: 一句话任务名
status: in_progress | blocked | done
verified: true | false
estimated_remaining_turns: N
---

## 目标
这次要达成什么，验收标准是什么。

## 已完成
- 做了什么；对应文件/提交/命令

## 已验证
- 跑了什么命令，通过/失败数量
- 界面类：截图路径
- 没有验证的写「无」

## 未验证 / 风险
- 哪些只是假设，没跑过
- 已知会坏的边界

## 决策
- 做了什么选择，为什么
- 被否掉的方案和原因

## 文件
- 关键文件路径（5–10 个）
- 不要贴大段代码

## 下一步
1. 具体的下一步，按顺序
2. 每步怎么验证

## 未决问题
- 需要用户拍板的事
- 需要下一个会话先查清的事

## 环境状态
- 未提交改动、后台进程、端口、迁移、数据状态
```

## 写法

- 区分「已验证」和「假设」，不要把假设写成事实。
- 引用文件路径，不要复制内容；下一个会话会自己读。
- 不写闲聊、死路、meta 评论。
- 不写密钥、token、密码、隐私数据。
- 文档控制在 800 字以内；超了说明重点没提炼。

## 一键换会话：`/switch`

`/switch` 不再追问，直接执行：

1. 目标：`$ARGUMENTS`；为空就从当前对话自然延续。
2. 写 ≤10 行交接，只写硬事实：目标、已完成、下一步（最多 3 条）、约束/未决。
3. 调用 `handoff_session(prompt=<交接>, files=<必要文件>)`。
4. 只回复「已开新会话」。

只带与新会话直接相关的文件，最多 8 个。学习任务带 `state.md`、当天 `daily/`、`profile.md`；代码任务带相关源码/测试/配置。

## 为什么是手动的（Stage 0）

最初设计过自动交接：达到 token 阈值或阶段边界就自动换会话。后来放弃，原因：

- 自动判断阈值不可靠；误切一次，返工成本远高于省下的 token。
- 长会话在缓存命中时很便宜；自动交接的收益主要是质量，不是省钱。
- 手动触发更可控，也更容易积累「本可以交接 / 不该交接」的真实例子。

现在的策略：先记录数据（`stage0-log.js`），由用户自己判断时机；只有在真实数据支持时，才考虑自动化。

## 成本逻辑

- 缓存命中价通常远低于未命中价；长会话本身可能很便宜。
- 只有剩余轮数超过盈亏平衡点，且处于任务阶段边界，才值得换会话。
- 热缓存下生成交接很便宜；冷缓存可能比不交接更贵。
- 真正贵的是失败重试和返工，不是交接本身。
