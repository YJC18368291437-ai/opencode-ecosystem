# 全局规则（AGENTS.md）设计

`config/AGENTS.md` 通过 `opencode.json` 的 `instructions` 注入每个会话。它不是代码，而是对模型行为的约束；目标是把「怎么做」写清楚，减少每次重复解释。

## 语言与风格

- 默认中文；先结论，再细节。
- 不确定就说不确定，并给出验证方式。
- 不写无关注释，不做没要求的重构。

理由：模型的默认输出容易变成「先铺垫再结论」。明确顺序可以节省阅读时间，也减少空话。

## 质量优先

- 不为了省 token 牺牲正确性；返工比省下的几分钱贵。
- 交差前按 `prove-it` 的格式给证据：做了什么、跑了什么命令、通过/失败数量、界面类附截图、哪些没验证到。
- 修 bug 先复现；改完跑测试 / lint / typecheck；项目没有这些命令就明确说明。

理由：模型很容易把「我改好了」当成「验证过了」。把证据格式写死，交差时就必须拿出命令输出或测试数量。

## 检索（Google / GitHub / 文档）

完整方法见 [search-playbook.md](search-playbook.md)。核心约束：

- 只在子任务互相独立、要广撒网时派子智能体；有先后依赖或需共享上下文就自己做。
- 原始材料落盘，回传「路径 + 3 行结论」，不回传全文，也不只给摘要。
- 结论必须指回 URL 或 `file:line`，否则标「未验证」。
- 来源优先级：官方文档 > GitHub 源码/README/tag/issue > 博客。
- 找不到写「未找到」，不许凭记忆补。

## 记忆

- 长期记忆在 `~/.config/opencode/memory/`，目录见 `INDEX.md`（已自动注入）。
- 只在出现「以后都」「记住」「这个项目约定」或做出重要决策时写。
- 按 `memory` skill 的归类规则写；拿不准放 `inbox.md`，不要乱建文件。
- 不写密钥、token、密码、隐私数据；写完更新 `INDEX.md`，每条保持一行。

理由：记忆写太多会变成聊天记录，写太少会重复踩坑。触发条件 + 索引上限是折中。

## 术语（所有会话）

- `known.md` 已注入：里面 mastered 的词不重讲，一句带过。
- 输出中首次出现 `known` 之外的技术术语 → 括号里给一句解释；不打断任务，不逐条展开。
- 一轮结束，最多列 3 个新词，用问题工具让用户三选一：
  - **懂了** → 写入 glossary，status 为 `mastered`
  - **没懂** → 写入 glossary，status 为 `introduced`，记卡点
  - **不记** → 不写任何文件
- 只有用户明确要求才贴全文或打开窗口。
- 不静默写入，不把每个术语都展开成段落。

理由：术语解释是学习系统的一部分，但不应打断主任务。三选一把「是否写入」的决定权交给用户，避免模型自作主张。

## 交接（Stage 0：手动）

- 阶段完成、连续两次卡住、上下文明显变满、或换不相关任务时，提醒用户可以考虑 `/handoff`。
- **不要自动开新会话，不要自动提交。**
- 写交接文档用 `handoff` skill 的模板，必须有「已验证 / 未验证 / 下一步 / 未决问题」。
- 文档放项目的 `.opencode/handoff/`，并提醒把它加入 `.gitignore`。

理由：自动判断阶段边界不可靠；误切的返工成本比省下的 token 高。手动触发更可控。

## 参数

- 价格、阈值、护栏在 `handoff.json`，全部可调。
- Stage 0 只读取 `prices`；其他字段在后续 Stage 才生效。

## 怎么改

1. 先改 `config/AGENTS.md` 的规则，再观察 3–5 个会话。
2. 如果规则需要机械执行，改成 command 或 plugin，而不是继续加文字。
3. 如果规则只适用于某个项目，放进项目的 `AGENTS.md` 或 `.opencode/`，不要污染全局。
